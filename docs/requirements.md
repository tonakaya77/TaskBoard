# TaskBoard 要件定義書

## 1. プロジェクト概要

### 1.1 背景
タスクがメモや頭の中に散らばっていると、どこまで進んだか、いつまでにやるべきかがわからなくなる。

### 1.2 目的
タスクの進み具合と期限をひと目で確認できる、Trello風のタスク管理Webアプリ「TaskBoard」を作る。

### 1.3 位置づけ
RaiseTech の課題として作る。要件定義から設計・実装までを一通り経験することも目的に含む。

### 1.4 ドキュメント構成
要件定義書には、要件の概要をまとめる。詳細は、次のドキュメントに分けて書く。

## 2. 機能要件

1人のユーザーが、複数のプロジェクトでタスクの進み具合と期限を管理できるようにする。主な機能は次のとおり。

- ログイン・ログアウト（アカウントは初期データで用意する）
- プロジェクトとステータス（列）の管理
- タスクとサブタスクの管理、ドラッグ＆ドロップでの移動と並び替え
- サブタスクの進み具合の表示（カードに、完了した数 / 全体の数を出す。例：1/3）
- 期限アラート（期限が近いタスクは黄色、当日と期限超過は赤）
- 緊急度の表示（タスクに緊急度（高・中・通常）を設定する。高は赤、中は黄で、カードの左端の色帯とタイトル前のバッジで示す。通常は何も出さない。タスク詳細・ダッシュボード・カレンダーにも表示する）
- ダッシュボード（今日やるタスクと、期限が近い順のタスク一覧）
- カレンダー（期限の日にタスクを表示する。今日の日付には印をつける）

詳しくは [機能設計](functions.md) の「機能一覧」を参照。

## 3. 非機能要件

| 分類 | 要件 |
|---|---|
| 対応環境 | PCとスマホのブラウザで使える（画面幅に合わせてレイアウトが変わるレスポンシブ対応） |
| 対応ブラウザ | 最新の Google Chrome |
| 日時 | 日時は日本時間（Asia/Tokyo）で扱う。サーバーの設定に関係なく、日本時間で日付を判断する |
| セキュリティ | パスワードはハッシュ化（暗号化）して保存する |
| セキュリティ | ログインしたユーザーは、自分のデータだけを見たり操作したりできる |
| セキュリティ | チーム機能を入れた場合は、ロールに応じた範囲のデータだけを見られるようにする（8章の拡張） |
| 性能 | 数値目標は設けない。普段の操作で待たされない快適さを目指す（最優先ではない） |
| 公開 | 課題としてインターネットに公開する予定。公開先は7章（技術選定）で決める |

## 4. 画面設計

画面は8つ（ログイン、ダッシュボード、ボード、カレンダー、タスク詳細、タスク作成・編集、プロジェクト設定、プロジェクト作成）。すべての画面に共通のサイドメニューを置き、PCとスマホの両方に対応する。

詳しくは [画面設計](screens.md) を参照。

## 5. ユースケース

アクターは「ユーザー」の1種類。ログイン、プロジェクト・ステータス・タスク・サブタスクの操作、期限の確認、今日やるタスクの選択など、緊急度の確認など、22のユースケースがある。

詳しくは [機能設計](functions.md) の「ユースケース」を参照。

## 6. データ設計

データは、ユーザー・プロジェクト・ステータス・タスク・サブタスクの5つのテーブルで管理する。日時は日本時間で扱い、「今日」は朝4時に切り替わる。

詳しくは [データベース設計](database.md) を参照。

## 7. 技術選定

バックエンドは Java / Spring Boot（講座の指定）、フロントエンドは React（Next.js は使わない）。データベースは PostgreSQL を仮決定とし、最終決定はあとで行う。フロントエンド＋バックエンド＋データベースの3層構成にする。

それ以外のツールと選んだ理由は [技術スタック](tech-stack.md) を参照。

## 8. 将来の拡張候補

- ユーザー登録
- チーム機能（プロジェクトへの招待、メンバー管理）
- プロジェクトロール（MANAGER / LEADER / MEMBER）
- 担当者の設定
- 通知（画面上部の通知欄で、招待・メンション・期限接近などを知らせる）
- メッセージ（プロジェクト内のやり取り。@メンションすると相手に通知が届く）
- タスクの依存関係
- ガントチャート
- Googleカレンダー連携
- AIサポート（タスク分解、抜け漏れ補助）
- タスク完了時のお祝い表示
- 「今日」の切り替え時刻をユーザーが設定する（初期値は朝4時）
- 今日やるタスクの中で、ドラッグして並べ替える
- 削除したデータを30日間残し、その間は元に戻せるようにする（論理削除とゴミ箱）

## 9. 制約事項

- フロントエンド＋バックエンド＋データベースの3層構成で開発する
- スクールの課題として開発する
- ログイン機能ありで開発する。ただし、提出の条件でログインなしを求められた場合は、ログイン機能を外す可能性がある（確認用のアカウントを初期データで用意し、ログイン情報を README に書く）
